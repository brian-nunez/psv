# Build the CLI, API and report UI as thin frontends over the core, tested on three tiers of data

## Context and Problem Statement

PSV is used three ways: the `psv` command line in a terminal or a pipeline, an HTTP API that a client streams a video to, and a report UI in the browser. The prototype that preceded this decision was a separate server program with its own job store: uploads were kept on disk under job IDs, the page polled for progress, frames were served on request, and the report page computed its own figures from a report wrapped in an ad-hoc envelope.

How do the CLI, the API and the UI consume the core package of [ADR-0002](0002-keep-detection-in-one-core-go-package.md), so that every medium gives the same answer and shows it the same way? And what data proves that they do, without making every pull request wait for full-resolution video?

## Decision Drivers

* The same report from every medium, in the `psv.report/v1` format of [ADR-0001](0001-use-psv-report-v1-as-the-shared-report-format.md).
* The same report UI whether a report comes from the API or a file.
* An API that stores nothing: no uploads or results kept after a request.
* One binary to install and release.
* Tests that prove the wiring on every pull request in minutes, while still checking real footage.

## Considered Options

* Thin frontends in one binary over the core: `cmd/psv` with `internal/standards`, a stateless `internal/server` and one embedded `internal/ui`
* Keep the prototype's design: a separate server with a job store, polling and a frame endpoint
* Analyse in the browser with a WebAssembly build of the core, with the UI as the only medium

## Decision Outcome

Chosen option: "Thin frontends in one binary over the core", because it is the only option in which every medium calls the same core functions, emits the same report and shows it through the same UI, while the server keeps no state.

### How each medium uses the core

| Medium | Code | Uses the core through |
| --- | --- | --- |
| CLI | `cmd/psv` (`psv [analyze]`) | `psv.AnalyzeFile`, `Analysis.Report`, `Report.WriteText`; sets `tool.version`, `source` and `standard` |
| Report file | `cmd/psv/render.go` (`psv render`) | `psv.DecodeReport`, then `ui.Render` |
| API | `internal/server` (`psv serve`) | `psv.Probe`, `psv.AnalyzeFile` and `Analysis.Report(true)`, streamed as newline-delimited JSON events |
| Report UI | `internal/ui` | Renders `psv.report/v1` documents; no analysis code |
| Presets | `internal/standards` | Maps `wcag22`, `trace24`, `broadcast` and `scene` to the core's presets for the CLI and the API |

* **CLI**: `psv <video>` and `psv analyze <video>` print text or a `psv.report/v1` report and exit with `0` for a pass, `1` for a fail and `2` on an error.
* **API**: `POST /v1/analyses?standard=…&name=…` takes the video as the request body, writes it to a temporary file for FFmpeg, and streams `received`, `progress` and finally `report` or `error`. Problems found before the analysis starts get `400`, `413`, `422` or `429`. The temporary file is deleted when the request ends, a closed connection cancels the analysis, and the run's upload directory is removed on shutdown.
* **Report UI**: one set of files, `internal/ui/assets/{index.html,app.css,app.js}`, embedded in the binary. `psv serve` serves them at `/`, where a chosen video streams to the API and the result renders. `psv render` inlines the same files, with the report in a `#psv-report` element, into one self-contained page. Frame previews come from the viewer's own copy of the video, never from the server.

### How it is tested: three tiers of data

| Tier | Data | Size | Used by | Runs |
| --- | --- | --- | --- | --- |
| Conformance | `testdata/pse-test-media`: the Trace RERC PSE test media, vendored at commit `ef78542` under its BSD 3-Clause licence. Patterns are rendered frame by frame in memory | 7.6 MB | `TestConformance`, all 378 checks; under `-short` with the race detector, the first failing video of each short set | Every pull request (`make test`) |
| Wiring | `testdata/clips`: three generated 320×180 H.264 clips (`pass.mp4`, `fail.mp4`, 60-second `long.mp4`), regenerated byte for byte by `make clips` | 108 KB | The CLI tests, `psv render` tests and API tests, including the API-versus-library comparison and the cancel test | Every pull request (`make test`) |
| Real footage | `testdata/examples`: full-resolution real-world videos, each with the `psv.report/v1` report of its last accepted analysis, regenerated by `make examples` | 15 MB | `TestExamples`, only with `PSV_TEST_EXAMPLES` set | On demand: `make test-examples`, or the Examples workflow, one job per video |

### Consequences

* Good, because the CLI and the API cannot disagree: both call `psv.AnalyzeFile`, and the API test checks the API's report against the library's for the same clip, frame by frame.
* Good, because a report renders identically from the API or a file: `TestRenderMatchesServedUI` checks that `psv render` inlines exactly the files the server serves.
* Good, because the server has no state to clean up, back up or secure beyond the life of a request.
* Good, because one binary ships everything, so a release is one file per platform.
* Good, because pull requests stay fast: `make test` takes about 2.5 minutes with 4 cores, against about 18 minutes on 12 cores when the CLI and API tests decoded full-resolution footage.
* Bad, because the server cannot show a frame or a report after the request ends; a client that wants them keeps the video and the report itself.
* Bad, because the server waits for the whole upload before analysing, since FFmpeg cannot read every MP4 from a non-seekable stream.
* Bad, because real footage is no longer checked on every pull request; a change that alters real-world results is caught only when the Examples workflow or `make test-examples` is run.
* Bad, because the example videos are third-party footage committed to a public repository.

### Confirmation

* `cmd/psv/main_test.go`: exit statuses, the report header and `psv -format json -frames | psv render`.
* `internal/server/server_test.go`: streamed events, the report against `psv.AnalyzeFile`, every error status, the busy limit, client cancellation, upload removal and the served UI.
* `internal/ui/ui_test.go`: the rendered page inlines the served files and embeds the report safely.
* CI runs `make test` on every pull request; the Examples workflow runs `TestExamples` on demand.
* Review rejects analysis code in `internal/ui/assets` and detection code in `cmd/` or `internal/`.

## Pros and Cons of the Options

### Thin frontends in one binary over the core

* Good, because every medium is a few hundred lines of wiring around the same core calls.
* Good, because the report UI exists once.
* Good, because the API keeps nothing.
* Neutral, because the frontends live in `internal/`, so other Go modules cannot import them; they import the core instead.
* Bad, because frame previews depend on the viewer having the video.

### Keep the prototype's design: a separate server with a job store, polling and a frame endpoint

* Good, because the server could show frames and reload a report by job ID at any time.
* Bad, because uploads and results stay on the server, which then needs retention, cleanup and access rules.
* Bad, because the report page computed figures and wrapped the report in its own envelope, so its JSON differed from the CLI's.
* Bad, because it was a second program to build and release.

### Analyse in the browser with a WebAssembly build of the core, with the UI as the only medium

* Good, because a public static page could analyse video with no server.
* Bad, because analysis under WebAssembly ran at 6.6 fps at 1080p, minutes per minute of video.
* Bad, because browser decoding could change verdicts on borderline videos relative to FFmpeg.
* Bad, because pipelines still need the CLI, so the browser could not be the only medium.

## More Information

* The README's "Report UI" and "API server" sections document the commands and endpoints; `docs/testing.md` documents the test tiers.
* The CI workflow (`.github/workflows/ci.yml`) runs `make test`; the Examples workflow (`.github/workflows/examples.yml`) runs the real-footage tier.
* Revisit if the server needs to keep results, for example to share a report by link: that is a change of trust boundary and gets its own ADR.
